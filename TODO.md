- [x] **Stock oversell race condition** — fixed 2026-09-19. `CreateOrderCommandHandler` (`Application/Orders/Commands/CreateOrderCommand.cs`) now wraps the stock-check-and-decrement loop in an explicit `BeginTransactionAsync`, and reads each `Product` via `FromSqlInterpolated("SELECT * FROM Products WITH (UPDLOCK, ROWLOCK) WHERE Id = {productId}")` — pessimistic locking. A second concurrent request for the same product blocks on the `UPDLOCK` until the first transaction commits, then sees the post-commit `Stock` value, so `Product.RemoveStock`'s existing invariant check correctly rejects it instead of both succeeding. No schema change/migration needed (chosen over an EF `RowVersion`/optimistic-concurrency approach, which was tried first — see [[project_stock_oversell_fix]]).
- [ ] **Possible deadlock on multi-item orders.** The pessimistic-locking fix above locks each `Product` in `request.Items` order via `UPDLOCK`. Two concurrent orders that touch the same two products in reverse order (A: X then Y; B: Y then X) can deadlock — SQL Server kills one transaction as the deadlock victim, raising a `SqlException` (error 1205) that isn't currently caught anywhere, so it'd surface as an unhandled 500. Fix: sort `request.Items` by `ProductId` before the locking loop so all requests acquire locks in the same order.
- [ ] **Resource-ownership gap.** `PaymentDetailsController.GetPaymentDetails(id)`, `GetPaymentDetailsByName(name)`, `DeletePaymentDetails(id)` take an id/name with **no check it belongs to the calling user** — any authenticated user can view/delete another user's card by guessing an id. Fix is a per-resource ownership check inside the handler (pattern already correct in `GetMyCards`/`PostPaymentDetails` via `ClaimTypes.NameIdentifier`).

Every `AdminOnly` endpoint (category/product writes, order list, payment-detail list) is unreachable by anyone, including the owner. ### Improving DDD / Architecture
- [ ] **No repository abstraction + no explicit Unit of Work** — every command handler injects the concrete `PaymentDetailsContext` (EF Core) directly. Application should depend on domain-owned abstractions (`IOrderRepository`, `IProductRepository`, ...) with EF as one implementation, plus an `IUnitOfWork` (`SaveChangesAsync()`) so handlers can coordinate multiple repositories under one atomic commit without knowing about EF Core. Note: `DbContext` already behaves as an implicit Unit of Work today (one `SaveChangesAsync` call = one atomic commit across all tracked entities) — a standalone `IUnitOfWork` wrapper isn't worth adding on its own before repositories exist, since it'd just be a thin re-wrap with no behavioral change. Do both together, not UoW first.

  - [x] **2026-09-20**: `IProductRepository` (`Domain/Catalogs/Repositories/IProductRepository.cs` — `GetByIdAsync`, `GetForUpdateAsync`, `AddAsync`), implemented in `Infrastructure/Persistence/Repositories/ProductRepository.cs`, registered in `Program.cs`. `CreateProductCommandHandler` and `AddStockCommandHandler` migrated off `PaymentDetailsContext`. Build-verified only — both are `AdminOnly` endpoints, blocked from full HTTP runtime verification by the open Admin-bootstrap gap (see Authorization section).
  - [x] **2026-09-20**: `CreateOrderCommandHandler` fully migrated — added `ITransactionRepository` (`Domain/Transactions/Repositories/`, `AddAsync`), `IIdempotencyKeyRepository` (`Domain/Shared/Repositories/`, `AddAsync`/`FindByKeyAsync`/`Detach`), `IPaymentDetailRepository` (`Domain/Payments/Repositories/`, `FindActiveForUserAsync`), all implemented in `Infrastructure/Persistence/Repositories/` and registered in `Program.cs`. Also extended `IUnitOfWork` with `BeginTransactionAsync()` returning a new `IUnitOfWorkTransaction` (`Domain/Common/IUnitOfWork.cs`) — needed because the pessimistic-lock reads have to run inside an explicit DB transaction that spans multiple repository calls, not just the final `SaveChangesAsync`; wraps EF's `IDbContextTransaction` so `Application` still never references EF types directly for this. One accepted, explicitly-flagged EF leak remains: the handler still catches `Microsoft.EntityFrameworkCore.DbUpdateException` for the idempotency-key race — closing that fully would mean translating `DbUpdateException` inside `IUnitOfWork.SaveChangesAsync()` globally, which is a bigger, separate change affecting every handler, not just this one. **Fully runtime-verified 2026-09-20**: created an order (200, stock 7→6, `Transaction` row linked correctly), replayed with the same `Idempotency-Key` header (200, same order id returned, no duplicate created), then cancelled it (204).
  - [ ] **Not yet migrated**: command handlers across Categories, Currency, Users, PaymentDetails (Orders and Products aggregates are now fully done). Query handlers (`GetOrderByIdQuery`, `GetOrdersByUserIdQuery`, `GetAllOrderQuery`, `GetAllProductQuery`) deliberately left on direct `DbContext` — they're read-side cross-table projections (joining `Users`/`Currency`/`Categories` into DTOs), not aggregate loads, so wrapping them in a repository adds indirection with no benefit; only command/write handlers go through repositories. Note this is a knowing, named divergence from strict Clean Architecture's inward-only dependency rule (Application still references `PaymentDetailsContext` on the read side) — accepted as the standard CQRS trade-off, not an oversight.
- [ ] **Cross-aggregate mutation in a single transaction** — `CreateOrderCommandHandler` loads a `Product`, mutates it, creates/saves a new `Order`, *and* (as of 2026-09-19) a `Transaction`, all in the same `SaveChanges` call. This was a deliberate choice for the `Transaction` (financial data needs atomicity with the order, not eventual consistency via a domain event — see the linkage note in Done), but it does mean the handler now spans three aggregates in one commit. One transaction touching one aggregate is still the textbook DDD shape; revisit only if this handler's scope keeps growing.
- [ ] **Domain event dispatch has no durability, and a side-effect failure can fail an already-committed write.** Verified 2026-09-21 by tracing every command handler (`CreateOrderCommand`, `CreatePaymentDetailCommand`, `CreateCategoryCommand`, `RegisterUserCommand`, `AddStockCommand`): each calls its own `SaveChangesAsync`/commit *before* returning, so `DomainEventDispatchBehavior` (`Application/Common/Behaviors/DomainEventDispatchBehavior.cs:33`) always dispatches events *after* the primary entity is durably committed — ordering itself is fine, no reorder fix needed. The real gaps:
  - If a handler like `OrderCreatedEventHandler` throws (e.g. `_emailService.SendAsync()` fails), the exception propagates out of the pipeline and fails the whole request even though the write already succeeded — caller sees a failure for something that actually happened.
  - Event-handler side-effect writes (`PaymentCreatedAuditHandler`'s `Log` row, etc.) are persisted by a second, separate `SaveChangesAsync` (`DomainEventDispatchBehavior.cs:34`) that isn't atomic with dispatch — if it fails, the email already went out but the audit row is lost.
  - Pending events live only in `AggregateRoot.DomainEvents`, an in-memory list — if the process crashes between the handler's commit and the behavior's dispatch, the event (and its side effects) is silently dropped forever, with no record it should have fired.
  - Cheap partial fix (do regardless): wrap `_dispatcher.Dispatch(events)` in try/catch-and-log so a side-effect failure can't fail an already-committed request.
  - Real fix for the durability gap: transactional **Outbox** — persist events as rows in the same `SaveChangesAsync` call as the aggregate (natural seam: `UnitOfWork.SaveChangesAsync`, currently a one-line passthrough in `Infrastructure/Persistence/UnitOfWork.cs:15-16`), dispatch as a separate step afterward, mark processed. Prerequisite: domain events currently carry live entity references (`OrderCreatedDomainEvent.Order`, `ProductStockAddedDomainEvent.Product`) instead of plain data (ids/values) — not serializable as-is, needs flattening first across Orders/Catalog/Payments/Users events and their handlers.

- [ ] **`PaymentDetail` uses a bare `bool Active` + `Delete()`** instead of an explicit status concept — `Order` already shows the better pattern with `OrderStatus`. Consider a small status enum for consistency.
